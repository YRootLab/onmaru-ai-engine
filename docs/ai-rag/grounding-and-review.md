# 문장별 근거 검증과 사람 검수 정책

> 상태: 1차 출시 목표 계약. [RAG 저장 스키마](rag-storage-schema.md)의 문서·청크·출처 revision을 사용한다. 자동 검사는 **근거의 존재·연결·현재 자격**을 보증하고, 문장의 의미상 참 여부는 평가셋의 사람 검수로 확인한다.

## 출력 계약과 신뢰 경계

FastAPI의 닫힌 출력은 `places[{placeId,reasonClaims[]}]`, `summaryClaims[]`, `citations[]`로 제한한다. 각 `claim`은 `{claimId,text,kind,evidenceIds[]}`이다. `kind`는 `FACT`(역사·건축·작품 관계·접근성 등 확인 가능한 사실), `INTERPRETATION`(근거에서 허용되는 방문 의미), `PREFERENCE`(조용함/가족 적합 등 조건부 추천 이유), `CONNECTOR`(장소 간 단순 연결 문구) 중 하나다. claim당 근거는 1~3개, 전체 답변 근거는 최대 12개다. 모델이 반환한 URL·출처 제목·임의 장소명은 그대로 게시하지 않는다. 사용자는 서버 evidence registry에서 만든 출처 제목과 개정 시각을 본다.

현재 provider의 자유 `narration` 기반 proposal에서 이 구조로 바꾸는 것은 **새 내부 계약 변경**이다. 모델/어댑터의 JSON schema, FastAPI validator, Spring renderer, SSE fixture를 같은 구현 변경에서 교체한다. 기존 출력의 자유 문장을 claim으로 자동 변환했다고 간주하지 않는다.

## 자동 검증: fail closed

1. JSON schema의 추가 필드·길이 초과·중복 ID·HTML/Markdown/URL·제어문자를 거부한다. 문장 수·답변 전체 길이·장소 최대 5개를 제한한다.
2. 모든 `placeId`와 `evidenceId`가 해당 run의 allowlist에 있는지, evidence가 같은 장소·활성 corpus revision·허용 source revision의 청크인지 검사한다. claim의 장소와 evidence의 장소가 다르면 거부한다.
3. Spring이 최종 저장 직전에 장소 공개 자격, source 이용 권리/철회, 지역·고정·제외 조건을 다시 조회한다. 철회 source의 claim은 제거하고 근거가 없는 장소 카드도 제거한다. 남은 카드가 3개 미만이면 부족 상태를 명시한다.
4. 정형 값(주소·지역·분류·작품 관계)은 모델 문장보다 canonical SQL/검증 관계를 우선한다. 불일치하면 그 claim을 삭제하고 검증된 정형 값만 사용한다. 숫자·날짜·인명·고유명사는 근거 본문에 같은 정규화 값이 있는지 확인한다. 값이 없으면 보류한다.
5. 최종 `text`는 검증된 claim의 순서 있는 렌더링 결과로만 생성한다. 모델이 claim 밖에 써 둔 자유 `narration`은 게시하지 않는다. 단순 인사·전환 문구는 서버가 가진 고정 템플릿만 사용한다. SSE는 이 최종 `text` 저장 후에만 보낼 수 있다.

이 검사는 **의미상 지지의 충분조건이 아니다**. 근거가 같은 장소를 언급해도 시간·인과·관계를 과장할 수 있다. 자동 검증으로 의미를 확신할 수 없는 claim은 게시하지 않고, 확인된 짧은 설명 또는 `근거가 부족해 자세한 설명은 어려워요`로 대체한다. 특히 추정 영업시간·실시간 혼잡·접근성 보장은 근거와 현재성이 부족하면 항상 보류한다.

## 의미상 지지 간극을 줄이는 단계

첫 구현은 생성기의 문장을 사후 채점하는 대신, **주장 가능한 사실의 범위를 생성 전부터 좁힌다.** 청크에는 원천 문서의 시작·끝 offset과 문단 ID를 보존하고, LLM에는 해당 질문에 선택된 짧은 근거 span과 source revision을 준다. LLM은 복합 문장 대신 한 claim에 하나의 검증 가능한 사실을 작성하고, `evidenceIds`와 인용 span ID, `claimType`(정형 값·관계·해석·취향), 시간 범위, 확실성 표현을 반환한다. span ID는 서버가 만든 allowlist만 허용한다. 출력 schema 변경은 [요청 생명주기](request-lifecycle.md)의 내부 계약 버전과 함께 한다.

검사 순서는 (1) span의 실제 내용·offset·현재 source revision 확인, (2) 장소·작품·인물·날짜·숫자 및 부정·비교 대상의 일치, (3) 관계·시간·인과의 방향과 강도 확인, (4) 주장의 범위가 근거보다 넓지 않은지 판정이다. 1~2는 코드와 canonical 관계로 결정할 수 있는 유형만 자동 통과시킨다. 3~4는 문자열 포함만으로 통과시키지 않는다. 한 claim에 서로 다른 두 사실이 있거나 근거의 시점과 주장의 시점이 다르면 분리·축소하거나 보류한다. `INTERPRETATION`/`PREFERENCE`는 사실 보장처럼 쓰지 않고 조건부 어조와 출처를 표시한다.

의미 판정기는 **오프라인 평가 후보**로 시작한다. 공개·합성 평가셋의 claim과 근거 span에 `SUPPORTED/PARTIAL/UNSUPPORTED/NOT_CHECKABLE` 사람 라벨을 붙이고, NLI 또는 LLM 평가기의 오탐(근거 없는 claim을 허용)과 미탐(지지되는 claim을 보류)을 유형별로 비교한다. Microsoft도 groundedness를 생성 답변의 주장과 제공 문맥의 대응 관계로 평가한다. [Microsoft RAG 평가 안내](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase). 판정기가 사람 라벨과 지연·비용 기준을 통과하기 전에는 온라인 게시 허가자로 사용하지 않는다. 도입하더라도 **추가적인 보류 신호**로 쓰고, 모델 점수 하나만으로 허위 사실을 승인하지 않는다. 판정기 오류·timeout은 자동 통과가 아니라 해당 claim 보류 또는 확인된 정형 설명으로 축소한다.

이 설계로도 모든 자연어 의미의 진실을 자동 증명할 수는 없다. 출시 게이트는 금지 출처/관계 위반 0건, 봉인셋 사람 검수의 claim 지지율, 유형별 보류율과 답변 유용성을 함께 본다. 운영 중 신고된 오류는 source 오류·검색 누락·생성 과장으로 분류해 승인된 합성 재현 사례로 만들고 다음 평가셋 버전에 추가한다.

## 허용·부분 허용·보류 결정표

| 조건 | 처리 |
|---|---|
| 모든 claim의 ID·source·현재 공개 검증 통과, 평가에서 해당 유형의 지지율 게이트 통과 | 확정 답변과 출처 게시 |
| 한 장소의 일부 claim만 검증 실패 | 해당 claim만 삭제; 카드에는 남은 검증된 이유가 있을 때만 표시 |
| 장소 카드의 이유가 모두 보류 | 그 장소를 제거; 남은 장소가 1~2개여도 억지로 채우지 않음 |
| 출처는 있으나 질문의 특정 역사/작품 관계를 뒷받침하지 못함 | 해당 관계를 주장하지 않고 근거 부족 안내 |
| 근거 0건, source 철회, revision 불일치, claim 구조 파손 | LLM 결과 폐기; 검증된 기본 탐색 또는 명시적 실패. 추가 모델 호출 없음 |
| 과거 대화의 출처가 나중에 철회됨 | 과거 답변 텍스트는 기록으로 남기되 현재 이용 불가 표시; 새 답변 근거로 재사용 금지 |

## 사람 검수와 평가 라벨

출시 전 봉인셋의 **모든 FACT·INTERPRETATION·PREFERENCE claim**을 두 명이 독립 검토한다. `SUPPORTED`, `PARTIAL`, `UNSUPPORTED`, `NOT_CHECKABLE`로 라벨링하며, `SUPPORTED`만 지지율 분자에 포함한다. `PARTIAL`은 근거가 일부만 말하거나 강도가 과한 경우다. 의견 차이는 근거 청크·원천 offset을 열어 조정하고, 조정 전·후 라벨과 이유를 보존한다. 검수자가 근거에서 사실을 확인할 수 없으면 모델의 유창함으로 통과시키지 않는다.

출시 뒤 모든 답변을 사람이 실시간 검수하는 운영은 전제하지 않는다. 다음 경우는 **우선 검수 큐**에 넣고 동시에 사용자에게는 자동 검증된 부분만 보여 준다: 새로운 주제 code·출처 종류, low confidence 검색, 3개 미만 결과, 철회 직후 24시간, 모델/프롬프트/청킹 변경, 안전 필터 경계 사례, 사용자 오류 신고. 검수 큐에는 원문 회원 질의 대신 재현 가능한 익명 fixture와 공개 근거 ID를 사용한다. 실제 대화 원문을 검수에 쓰려면 별도 동의·접근권한·보존 규칙이 먼저 필요하다.

사람 검수는 같은 원천의 내용 오류를 발견하면 Spring 원천 검수 상태를 수정하거나 source를 철회하는 경로로 연결한다. 수정 전까지 같은 근거가 반복 사용되지 않도록 revocation 차단 집합에 반영한다. 주간 보고는 claim 지지율, `PARTIAL/UNSUPPORTED` 유형, 출처별 오류, 자동 보류율, 신고 후 수정 시간을 포함한다. 평가/운영 연결은 [평가·환경 검증](evaluation-and-environment-tests.md)을 따른다.
