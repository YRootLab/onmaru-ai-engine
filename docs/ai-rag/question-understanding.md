# 여정 질문 해석 사전·결정 규칙

> 상태: 1차 출시 목표 계약. Spring은 개인정보를 제거한 `safeQuery`와 확정 구조화 상태를 FastAPI AI 엔진에 보낸다. AI 엔진이 `questionFrame`, 승인 코드의 `retrievalExpression`, 의미를 보존한 로컬 `semanticQuery`와 route를 제안하고 Spring이 공개·권한 경계를 승인한다. 사전은 버전형 자료이며 이 문서의 코드·동의어가 최소 출시 범위다. 구현 시 같은 version의 기계 판독 fixture를 Spring·FastAPI에 배포한다.

## 입력 정규화와 순서

1. 기존 공개 API의 입력 길이 상한 500자를 유지한다. Unicode NFC, 공백 축약, 일반적인 문장부호 정규화만 한다. 부정 표현·따옴표 안 명칭·숫자 순서는 제거하지 않는다. 전화번호·이메일·비밀키처럼 개인/민감 정보가 섞이면 모델로 보내지 않고 해당 부분 제거 요청을 안내한다.
2. `canonical 장소/지역/카테고리 별칭 → 날짜·실시간·범위 밖 판정 → 부정 범위 → 연산/주제/조건 추출 → 직전 확정 카드 지시어 해소 → 충돌 검사` 순서로 해석한다. **가장 긴 별칭 일치**를 우선하고 같은 길이의 동명이인은 지역 또는 직전 확정 ID로만 해소한다. 남는 중의성은 한 가지 확인 질문이다.
3. 사전은 `{version,code,kind,displayLabel,synonyms[],searchAliases[],status}`로 AI 엔진에 배포한다. Spring은 승인 가능한 canonical ID·필드 및 사전 version 계약만 확인하고 동의어 해석 규칙은 복제하지 않는다. code를 임의 문자열이나 provider 입력으로 만들지 않는다. 별칭 추가도 평가 fixture와 함께 version을 올린다. 매칭 규칙은 한국어 조사 경계를 허용하되 단어 내부 부분 문자열은 허용하지 않는다.

`questionFrame`은 라우팅·대상·응답 연산의 정본이다. `retrievalExpression`은 검색용 긍정/부정 개념과 공개 엔티티 ID를 보존한다. `한적한 아이와 갈 곳`은 `QUIET`와 `FAMILY_SUITABILITY` 둘 다 남겨야 한다. AI 엔진이 허용 code로 표현하지 못한 의미를 버리고 일반 추천으로 바꾸지 않는다. **`semanticQuery`는 사용자의 여행 의도에서 개인 식별·비밀·연락처·자유 URL을 제거한 짧은 한국어 검색 문장**이다. 코드로 환원되지 않는 허용된 표현의 순서·수식·부정 범위를 최대 240자로 보존한다. AI 엔진은 Spring이 비식별화한 `safeQuery`와 확정 구조화 상태만 받아 `semanticQuery`를 만든다. Spring은 원문→`safeQuery`의 삭제 span을 검증하고, AI 엔진은 `safeQuery`→`semanticQuery`의 의미 보존을 검증한다. 회원 원문 전체·과거 대화·식별자는 전달하지 않는다. 개인정보 여부나 의미 보존이 불확실하면 임의 재작성 대신 한 가지 확인 질문을 한다. AI 엔진은 같은 사전·승인 ID와 semanticQuery를 대조한 뒤 BM25·embedding·reranker에 사용하며, 부정/제외 hard filter는 구조화 계획만으로 강제한다. 검색 문장은 일반 로그·trace·평가 원문에 쓰지 않는다. 외부 Gemini에는 semanticQuery 원문을 전달하지 않고 승인된 조건·안전한 표현 유형·근거만 보낸다.

Spring은 개인정보·비밀정보 제거와 입력 안전 검사를 맡고, AI 엔진은 공개 장소명·지역명·여행 속성 표현의 **safeQuery span만** 추출한다. 각 span의 시작/끝, 대응 code/ID, 부정·수식 관계와 제거 이유를 요청 메모리에서 검증한다. 연락처·이메일·URL·주소·비밀키·식별자 패턴이 span에 걸리거나 미해석 문구가 핵심 조건이면 부분 문장을 억지로 완성하지 않고 확인 질문을 반환한다. 허용된 span의 접합은 검색용 문장일 뿐 사용자의 자연어 질문을 새 의미로 바꾸는 요약이 아니다. 예를 들어 `사람이 너무 많지 않은 한옥마을을 아이와 걷고 싶어`는 `너무 많지 않은`, `한옥마을`, `아이와`, `걷고 싶어`의 관계를 남기며, `북적이는 곳도 괜찮아`로 바꾸면 실패다. PII 탐지는 완전하다고 가정하지 않으므로 새 한국어 패턴과 우회형을 평가 fixture로 계속 보강한다.

## 1차 코드 목록

| 종류 | 허용 코드 | 대표 동의어·의미 |
|---|---|---|
| 연산 | `RECOMMEND`, `EXPLAIN`, `COMPARE`, `REFINE` | 추천/가볼 만한, 이야기/왜/어떤 의미, 비교/차이, 바꿔/빼고/추가 |
| 설명 초점 | `HISTORY`, `HISTORICAL_SIGNIFICANCE`, `ARCHITECTURE`, `CULTURAL_PRACTICE`, `VISIT_POINT`, `FAMILY_SUITABILITY`, `QUIETNESS`, `ACCESSIBILITY` | 역사/유래, 역사적 의미/관련, 건축/구조, 전통/체험, 볼거리/방문 포인트, 아이와/가족, 조용한/한적한, 무장애/휠체어 |
| 세부 주제 | `INDEPENDENCE_MOVEMENT`, `JOSEON_PERIOD`, `TRADITIONAL_MARKET`, `HANOK`, `K_CONTENT` | 독립운동/독립운동가, 조선시대/조선, 전통시장/재래시장, 한옥/고택, 촬영지/작품 관련 장소 |
| 동행 | `SOLO`, `COUPLE`, `FAMILY`, `FRIENDS` | 혼자, 연인/둘이, 아이와/가족, 친구와 |
| 분위기 | `QUIET`, `LIVELY`, `WALKABLE` | 조용한/한적한, 활기찬/북적이는, 걷기 좋은/산책 |
| 조건 연산 | `REQUIRE`, `EXCLUDE`, `PIN`, `UNPIN`, `RELAX` | 넣어줘/꼭, 빼고/말고/제외, 유지/고정, 고정 풀어, 조건 완화 |
| 정형 사실 | `ADDRESS`, `REGION`, `CATEGORY`, `PUBLIC_STATUS` | 주소/위치, 어느 지역, 분류/종류, 현재 볼 수 있는지 |

지역 code는 Spring `catalog_regions`, 장소 ID는 공개 canonical identity, 카테고리는 검수된 카탈로그 분류표를 사용한다. 별도의 자유 텍스트 지역·장소 code는 만들지 않는다. 위 목록 밖의 세부 역사 주제는 근거가 있어도 1차에는 무리하게 `HISTORY`로 접지 않고 주제를 좁혀 달라고 묻는다. `접근성`은 현재 정형 근거가 없으면 적합하다고 단언하지 않는다.

## 부정·복합 질문

| 입력 형태 | 결과 |
|---|---|
| `시장 말고 한옥`, `시장은 빼고 한옥` | `EXCLUDE(TRADITIONAL_MARKET)` + `REQUIRE(HANOK)`; 제외가 후보 검색 전에 적용됨 |
| `조용하지 않은 곳` | `QUIET`의 단순 제외로 뒤집지 않음. `LIVELY`로 표현 가능한지 확인 질문 |
| `서울 또는 경기` | 지역 OR 최대 2개; 한 지역 안의 카테고리/테마는 AND. `그리고`로 명시된 여러 지역의 동시 방문 가능성은 임의 판단하지 않음 |
| `한옥은 유지하고 시장만 빼줘` | 직전 확정 한옥 ID `PIN`, 시장 분류 `EXCLUDE`; 이후 턴에도 유지 |
| `주소도 알려주고 독립운동 이야기도` | 하나의 run에서 정형 `PUBLIC_ADDRESS`는 grant-bound Spring lookup(REST 기본 adapter), `EXPLAIN`은 RAG. 두 결과를 검증된 snapshot에서 합침; 한도는 LLM dispatch 한 번 |
| `A와 B의 차이와 주변 명소 추천` | 초점이 다른 두 연산이므로 한 가지 우선 질문을 요청; 임의로 질문을 누락하지 않음 |

하나의 run에서 **주연산 하나 + 부수 정형 사실 하나**까지만 처리한다. 설명/추천 같은 생성 연산 두 개 이상, 지역 OR 3개 이상, 서로 충돌하는 `PIN`/`EXCLUDE`, 해석 가능한 대상 3곳 이상은 확인 질문으로 좁힌다. 부정은 `안`, `않`, `말고`, `제외`, `빼`, `싫`의 문장 범위를 규칙 fixture로 판단하며 `조용하지 않은` 같은 형용사 부정은 임의 반대 속성으로 치환하지 않는다. `부산 말고 서울`은 이전 지역 부산을 제외하는 것이 아니라 이번 요청 지역을 서울로 교체한다.

## 다턴 우선순위와 모호성

현재 턴의 명시 조건 > 직전 확정 턴의 pin/exclude > 구조화 요약이다. 같은 속성의 명시 변경은 이전 값을 덮고, 새로운 제약은 누적한다. `여기`는 직전 확정 카드가 하나일 때만, `첫 번째/두 번째`는 직전 확정 카드 배열 인덱스로만 해소한다. 카드가 갱신·철회됐거나 여러 장소가 가능한 `이곳`은 다시 묻는다. 질문이 지역을 생략하면 thread의 확정 지역을 쓰고, 새 thread에 지역이 없더라도 지역 무관 추천이 명시돼 있고 전체 공개 후보가 허용되면 바로 탐색한다. 지역이 결과를 결정하는 필수 조건인데 빠진 경우에만 지역을 묻는다.

범위 밖·실시간 질문은 먼저 판정한다. 대상과 주제가 모두 확정돼도 해당 장소의 근거가 없으면 질문 해석 성공과 retrieval 실패를 구별해 `근거 부족`으로 답한다. `questionFrame` 표현율은 답 가능한 gold 질문 중 **대상·주제·연산을 모두 올바르게 보존한 비율**로 계산하며, 자동 확인 질문 비율과 잘못된 결합을 별도 보고한다.

## 필수 fixture 예시

| 원문 | 기대 frame 또는 경로 |
|---|---|
| `전주에서 조용한 한옥 3곳` | `RECOMMEND`, 전주, `REQUIRE(HANOK)`, `QUIET` |
| `두 번째 장소가 독립운동과 관련 있나요?` | 직전 카드 2번 ID, `EXPLAIN`, `INDEPENDENCE_MOVEMENT` |
| `그건 빼고 시장은 넣어줘` | `그건` 대상이 하나로 확정될 때만 `EXCLUDE(placeId)` + `REQUIRE(TRADITIONAL_MARKET)` |
| `한옥 말고 조용하지 않은 곳` | `EXCLUDE(HANOK)` + 분위기 확인 질문; 조용한 곳으로 잘못 추천 금지 |
| `A 주소와 B의 역사 알려줘` | 서로 다른 대상의 복합 연산 → 우선 질문 확인 |
| `오늘 영업 중인 곳` | 실시간 정보 범위 밖 안내; LLM 0회 |

출시 전 fixture는 별칭·동명이인·조사·부정·지시어·충돌·복합 질문을 각각 포함하며, 새 code/별칭을 추가하면 예상 frame을 사람이 검토한다. 평가셋과 판정 기준은 [평가·환경 검증](evaluation-and-environment-tests.md)을 따른다.
